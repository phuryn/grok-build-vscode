# CLAUDE.md — grok-build-vscode

VS Code sidebar and desktop client for Grok Build and OpenAI Codex, driven through the [Agent Client Protocol (ACP)](https://agentclientprotocol.com). The host owns presentation and provider metadata; each CLI owns its conversation state, tools, memory, and provider-specific plan enforcement.

The Remote Control server half — the AFK Pilot relay + browser client — is open source at [phuryn/afkpilot](https://github.com/phuryn/afkpilot), which also hosts the system-wide engineering docs (two-repo map, wire contract, auth, test matrix, CI/CD). The wire contract is mirrored: `src/remote-frames.ts` here ↔ `src/frames.ts` there; bump `REMOTE_PROTO_VERSION` in both on any incompatible change, and prefer additive, capability-detected changes. Issues for BOTH repos are tracked here (afkpilot's tracker is deliberately disabled).

## Status

See [CHANGELOG.md](CHANGELOG.md) for the current version and full release history (the Marketplace/GitHub-published build can lag the local working tree). The whole test suite is **binary-free** — CI uses fake Grok and Codex ACP fixtures; binary-dependent probes live separately in `research/*.cjs`. Grok Plan mode is enabled and enforced by the client safety gate (see `research/plan-mode.md` § Resolution); Codex plan review is an ordinary permission whose `allow_once` means implement — write/shell enforcement stays in the adapter/CLI, and Auto accept is suppressed by `effectivePlanActive`. Smoke-tested end-to-end on Linux, Windows-via-WSL, and the **native Windows build** (`irm https://x.ai/cli/install.ps1 | iex`) — `cli-locator` resolves `grok.cmd`/`grok.exe` and `terminal-manager` runs Grok-delegated commands under PowerShell on Windows (`pwsh`→`powershell`, mirroring the standalone CLI; #46), `$SHELL` (else `/bin/sh`) on POSIX.

This file is the project map: it describes the **current** architecture, not a per-version log.

**Editing discipline — keep this file lean.** When behavior changes, *rewrite* the affected lines to the new current state; do **not** append a note about what changed or why the old way was wrong. Concretely, none of these belong here:
- version-by-version history or "fixed in 0.2.x / removed in 1.4.x" → [CHANGELOG.md](CHANGELOG.md);
- bug post-mortems / "used to… / this broke because…" narrative → a code comment or `research/*.md`;
- evidence dumps ("one capture: 17.7s", "a real case: 74 messages") → `research/*`.

State the rule, name the function / constant / config-key an agent would grep for, and link the deep-dive — **one fact, one home**. Every feature already has a `research/*.md`; `docs/architecture.md` holds the event-flow detail; [docs/internal/ACP-feedback.md](docs/internal/ACP-feedback.md) is the upstream-facing summary of grok-CLI/ACP friction, agent-family wire differences, and our workarounds (update it when a new workaround lands or an old one becomes obsolete). If a paragraph explains *how we found* a bug rather than *how the code behaves now*, it's in the wrong file.

**Grok CLI compatibility.** The extension updates the CLI once per extension upgrade (`maybeUpdateCliOnUpgrade`), then probes `grok --version` each start (`resolvePlanModeAvailability`) to decide whether Plan mode is offered. A live, verified-old CLI latches Plan off for that session; an unreadable probe disables it but stays **re-checkable**, so picking Plan retries without a restart. The floor is `GROK_REQUIRED_VERSION`; known-broken Windows startup ranges are handled by `isStdioBrokenGrokVersion` / `maybePinBrokenCli`. Which versions, and why: [research/stdio-eof-regression.md](research/stdio-eof-regression.md) and [CHANGELOG.md](CHANGELOG.md) — deliberately not repeated here, per the editing discipline above.

## Build + test

```bash
npm install
npm test         # 4861 tests, a few seconds, vitest — all grok-free (incl. happy-dom DOM tests + fake-CLI ACP integration tests)
npm run test:perf # opt-in session-history perf simulation (NOT in npm test/CI; see § History pagination)
npm run test:integration # real VS Code Extension Host (~6s warm). NOT part of `npm test`;
                 # CI runs it as a second required job and `release.*` now gates on it too.
npm run e2e:lifecycle-host # long-lived real desktop host for the relay lifecycle e2e (not in npm test / CI)
npm run package  # → grok-vscode-phuryn-<version>.vsix (clears older *.vsix first; refuses a non-production REMOTE_RELAY_URL)
```

### Test taxonomy — three layers

There are **three** kinds of tests, and it matters which is which:

1. **`npm test` — grok-free unit/DOM/integration suite (4861 tests).** Pure logic, happy-dom tests that drive the real `media/chat.js`, a real-shell TerminalManager smoke, and a fake-CLI ACP integration suite (`test/fixtures/fake-grok-acp.cjs`). **Never spawns the real `grok` binary.** Runs in a few seconds with no network, no login, no subscription. This is the floor — every change keeps it green. (Two separate opt-in suites live outside `npm test`: `npm run test:perf` runs the session-history perf simulation — `test/*.perf.ts` via `vitest.perf.config.ts` — and `npm run test:integration` runs the `@vscode/test-electron` smoke below; both are matched only by their own config so they stay out of `npm test`.)
2. **CI — the *same* suite, plus a REQUIRED Electron smoke.** `.github/workflows/ci.yml`'s `test` job runs `npm ci && npm run compile && npm test` on a **matrix of `ubuntu-latest` and `macos-latest`** (`fail-fast: false`; the VSIX is packaged once, on Ubuntu) — **CI's `test` job ≡ layer 1, verbatim** (no `grok` binary, no auth, no subscription, so it *cannot* touch the real CLI — the whole reason layer 1 is grok-free). A second job, `integration`, runs the `@vscode/test-electron` smoke under `xvfb` (`npm run test:integration` — activate the extension, assert commands registered, resolve the webview via the *missing-CLI* onboarding path, then provision `test/fixtures/fake-grok-acp.cjs` through `provisionFakeGrok` so remote resume/`session/load` and matching-sessionId worktree tests run without a real CLI). Test-mode `activate` calls `isolateFromInstalledGrok` before any view can resolve; that latches `testForceMissingGrokCli` so `locateProvider("grok")` will not search config or PATH (an explicit provisioned path still wins). Resume assertions require a distinctive `updates.jsonl` marker to reach the client, `waitForSessionLoad` to settle, and a live ACP session afterward — `initialized` / a reserved session id / replay-before-the-RPC-result are not enough. (`startSession` swallows a failed load and still resolves the reservation.) It's a **required gate** (validated passing against a real VS Code Extension Host before landing; if a Linux/xvfb quirk ever surfaces, fix it rather than demoting the gate). The smoke is still grok-binary-free — it exercises host glue (activation, `getHtml`/CSP, `localResourceRoots`, command registration, hermetic ACP resume) the unit suite structurally can't reach. Compiles in isolation (`integration/tsconfig.json` → `out-integration/`), so it's out of `npm test` and the extension build.
3. **`npm run test:live` — on-demand pre-release suite against REAL grok (`scripts/live-tests.cjs`).** It covers the real handshake, capability drift, prompt/cancel/interject, fork/parallel/restore, plan enforcement, rewind, usage, and generative surfaces. The plan lane now uses native verdicts: its first same-turn `exit_plan_mode` response is `cancelled`, the second is `approved`, and the gate is lowered inside that response callback before implementation continues; `plan-cancel-rewind` uses native `abandoned` with no primer or marker turns. It reuses the compiled dispatch/gate/rewind modules and shipped webview helpers. The release scripts run it by default, but it needs a logged-in grok, burns credits, and never belongs in `npm test` or CI. A SKIP does not fail the gate; research probes remain manual one-offs.

**So:** local `npm test` == CI's `test` job (both grok-free) — but that is NOT all of CI: a second required job runs the grok-free Electron smoke, so `npm test` alone is a subset of what must pass. Mirror it with `npm run test:integration`, which `release.*` now gates on too. The real-grok tests are a separate, mandatory pre-release gate — always run before a tag/release (no need to ask), never on every commit.

**Standing test discipline.** Every `session.provider === …` branch has both-provider coverage. A wrapper that assumes a function's documented invariants carries that function's contract tests, including consumed-slot pagination. External-artifact fixtures mirror the real listing and layout, including multi-platform bundles and the Codex package structure. Every new filesystem or network stream has fault-injection coverage for asynchronous error paths.

### grok CLI version + updating

The native-Windows build (`irm https://x.ai/cli/install.ps1 | iex`) installs from the **stable** channel. The extension pins Windows to the supported build (`GROK_STDIO_DOWNGRADE_TARGET` in [src/cli-locator.ts](src/cli-locator.ts); see § Status → Grok CLI compatibility). **grok does not auto-update.** Updating is the explicit `grok update` command: `--check [--json]` checks without installing, bare `grok update` installs the latest on the current channel, `--stable` (default, weekly) / `--alpha` switch channels, `--version <X.Y.Z>` pins a build. `grok update` can only rename the binary when no grok process holds it open (else *"cannot rename locked executable"*), so the extension's update path tears the whole pool down and **awaits each process's actual exit** before updating; on Windows it `taskkill /T /F`-kills the process **tree** (grok backgrounds children that keep the binary locked) and retries once on a lingering lock (`isLockedBinaryError`). Re-run `npm run test:live` after any CLI update — the wire format is the thing that drifts.

## Known limits

Codex image generation is recognized only on a Codex-provider
`kind:"other"` / `title:"Image generation"` call. Completion maps to
`<codexHome>/generated_images/<sessionId>/<toolCallId>.png` only after UUID /
`exec-UUID` validation plus resolved containment, and flows through
`postGeneratedMedia`, giving VS Code, desktop, and remote the same media pipeline
and their normal surface-specific actions. `CODEX_HOME` overrides the platform
home; provider scoping prevents Grok user-derived tool titles from false-matching.

- Live child activity on grok 1.0.3+ is a compact stream inside the parent card (prose, thoughts, tool rows), not a nested inspector of the child's own session. Composer-era CLIs still send no child stream. Cold reload rebuilds cards from the lifecycle rail only.
- Generated media is served only when canonical containment proves it lives under the Grok session root or Codex `generated_images` root; trusted files may use a base64 `data:` URI when the current surface cannot serve that root
- No worktree UI
- The native diff editor is preview-only: it reconstructs full-file context from the file on disk and Grok's replaced-region metadata, but falls back to the region alone if the file is unreadable, oversized, or no longer matches; the write happens via `fs/write_text_file` after approval
- View placement: **default-homed in the Secondary Side Bar** (`viewsContainers.secondarySidebar` — requires VS Code ≥1.106, the `engines` floor; older hosts can't install this build — **Antigravity is on base 1.104** and refuses it, keeping the last compatible version). Relocation is one-click via Settings → Advanced → **Move view** (direct `vscode.moveViews` into the per-location containers — `src/view-move.ts`), or drag. Cursor's primary-side-bar context menu still hides the built-in "Move To" entry — the gear mover is the workaround. User moves persist; a persisted placement wins over the contribution default (*Reset Location* restores the default)

## Cross-platform notes

- `terminal-manager.ts` selects the shell via `resolveTerminalShell(platform, resolve, pref, posixShell)`: Windows runs the agent's commands under PowerShell (`pwsh.exe`→`powershell.exe`, else cmd.exe via `shell:true`) to mirror the standalone CLI (#46); POSIX `auto` uses `$SHELL` when it is an absolute path other than `/bin/sh`, whose basename is in the POSIX-grammar allowlist (`POSIX_SHELL_NAMES` — fish/nushell/tcsh get `/bin/sh`, because `posixSpawnArgv` hands them the agent's POSIX script directly), and which is a REGULAR EXECUTABLE file (a directory named `zsh`, or one with no execute bit, would fail every command with `EISDIR`/`EACCES`); else `/bin/sh`. POSIX spawn is `posixSpawnArgv`: peel grok's `/bin/bash -lc` wrapper (`unwrapGrokBashLoginWrapper`) and `spawn(host, ['-c', script], { shell: false })` so the host cannot exec that wrapper (issue #140; `GROK_SHELL=zsh` alone does not stop grok 1.0.x from sending `bash -lc`). Windows still uses Node `shell:` (`<shell> -c "<command>"`; pwsh + Windows PowerShell both accept `-c`, and Node passes the command string through faithfully; only cmd/bash-style `\"` escaping doesn't, which grok won't emit for a PowerShell target). `whichOnPath` skips the `\WindowsApps\` Store-alias stub. `grok.terminalShell` (`"auto"`|`"cmd"`, host-read → `setTerminalShellPreference`, cache-clearing) is the escape hatch to cmd.exe / `/bin/sh`. Don't hardcode shell paths. **The agent is told which dialect to WRITE for** via `GROK_SHELL` in its spawn env (`buildEnv` in `sidebar.ts` sets it from the pure `grokShellEnvValue(resolvedTerminalShell(), platform)` — `pwsh`/`powershell`/`cmd` on Windows; **never set on POSIX** — upstream builds the model-facing `Shell:` from `$SHELL` on Unix (`resolve_shell_display`) and reads `GROK_SHELL` there as a PATH to a shell binary it validates as executable, so a bare `zsh` never reached the model; running the shell `$SHELL` names IS the POSIX alignment. Never overrides a user-set value): grok's ACP mode otherwise describes the shell from its own host detection and can emit POSIX idioms for a PowerShell host (§2.9; the `Shell:` line in the model's first message tracks `GROK_SHELL`, `research/oss-surfaces-probe.cjs`). POSIX `$SHELL` vs `/bin/sh`: `research/posix-shell.md`. **The `pwsh`-vs-`powershell.exe`-fallback gap is real: Windows PowerShell 5.1 collapses any non-zero native exit to 1 (pwsh 7 preserves it) and rejects `&&`/`||` chains (pwsh 7 accepts them) — install pwsh 7 for full parity.** A fresh shell spawns per command, so the profile re-runs each time (matches standalone's reachable functions, but adds latency and any profile stdout can prepend to captured output; on a `Restricted` execution policy 5.1 skips the profile + warns). The agent only acts on zero-vs-non-zero, which is preserved. Root cause + probe evidence: `research/powershell-terminal.md`.
- `cli-locator.ts` reads `HOME` / `USERPROFILE` env vars first (testability), falls back to `os.homedir()`. Uses `where` on Windows, `command -v` elsewhere. Checks `.cmd`/`.exe`/`.bat` extensions on Windows.
- Tests use `node -e "..."` everywhere, so commands are deterministic across platforms — don't add `pwd`, `awk`, `sleep`, `true`, etc.

## Publishing

**Release procedure — ALWAYS tag + create a GitHub Release (with the `.vsix` attached) on a release push to `main`** (standing convention; mirrors the `v1.0.0…` tag history + GitHub Releases):

**The release scripts run the gates, publish the GitHub Release and Open VSX, and install locally** — after bumping the version + writing the changelog section (step 1, user-initiated), run:

```bash
pwsh scripts\release.ps1        # Windows (native) — what we use here
./scripts/release.sh            # macOS / Linux / WSL — desktop installer handoff is manual
```

Both scripts read the version from `package.json`, run the gate, build the vsix, commit the working tree, push `main`, wait for CI on the pushed SHA, create the annotated tag, and run `gh release create` **with the vsix attached** — extracting the matching `## X.Y.Z` changelog section as the release notes. Both then run `npm run publish:ovsx` and install the released vsix into local editors. `-DryRun`/`--dry-run` previews the publish actions after the gate and packaging; `-NoTest`/`--no-test` skips the gate. Both refuse to run off `main` or when the tag already exists. **Open VSX is published by the scripts; the VS Code Marketplace remains manual and Paweł-only** (step 6).

PowerShell also dispatches `.github/workflows/desktop-release.yml` against the release tag and waits for `.exe`, `.dmg`, and `.AppImage` assets. Missing installers are recorded, local installation is attempted (unless `-NoInstall`), and the script ends with an incomplete-release error naming the missing artifacts. `-SkipInstallers` explicitly skips that check. Bash prints the manual dispatch and asset-verification commands; its work is incomplete until those installers are attached.

What the script encodes, step by step:

1. Bump `version` in `package.json` and add the dated section to `CHANGELOG.md`. **The bump is a PATCH (+0.0.1) unless Paweł has explicitly said otherwise** — a minor or major needs his direct approval and is never inferred from how much changed (§ Repo conventions). The test is whether users gain something they could not do before, not whether the diff is large or the change is visible: 3.16.0 should have been 3.15.1, because a running elapsed count on an existing waiting indicator is a refinement of an affordance that was already there. Compare against what this project's own minors have carried — 3.14.0 added three connectors and cut a 46-second conversation load to 191ms; 3.15.0 rebuilt what a `Read` row is. Spending a minor on less makes the next real one say less. As part of this pass, **review the release-facing docs for staleness against what actually ships** — this review is a required step, not optional:
   - `README.md` — features / screenshots / install matrix.
   - **`README.marketplace.md` — the STORE listing, and a separate file.** `npm run package` ships it via `vsce package --readme-path`, so this is what the VS Code Marketplace and Open VSX render; `README.md` is only the GitHub page. Every edit to one is a decision about the other: the two carry the same feature list (keep the ordering in step), but deliberately different heroes — the listing sells the **extension**, so a desktop-app screenshot is off-message there. Its images are absolute `raw.githubusercontent.com/…/main/…` URLs, so **deleting or renaming anything under `docs/screenshots/` breaks the published store page** — remotely, after the release, with nothing local to notice. 3.2.1 shipped exactly that (alt text and a broken-image icon on Open VSX) because only `README.md` was updated. `test/readme-images.test.ts` now fails on a dangling reference in either file; it does not check that the two agree on content, which stays a judgement call.
   - `TESTS.md` — test plan vs. what actually ships.
   - `CLAUDE.md` — the project map (§ Module map, § ACP surfaces, § Known limits, the test-count floor): does it still describe the current architecture? It deliberately **doesn't** hardcode the version (it points to the changelog), so it needs no version edit — but its prose can go stale as behavior changes.
   - `docs/architecture.md` — the architecture doc: keep it in sync with new modules / event flows / surfaces.
   - `package.json` itself — description, `engines`, `categories`, `contributes`.

   Keep `CHANGELOG.md` entries **terse** (1–3 bullets per release under Added/Changed/Fixed; deep detail belongs in commits / `research/`, not the changelog); releases before the current minor live in `docs/CHANGELOG-ARCHIVE.md` (linked from the foot of `CHANGELOG.md`).
2. `npm test` (4861-test floor, all green) + `tsc -p . --noEmit` clean + **`npm run test:integration`** (the real Extension Host — `npm test` is only CI's `test` job, and CI runs this as a SECOND required job; without it a release can be tagged and published before CI goes red), **and `npm run test:live` against real grok — mandatory, run without asking**. The `release.*` scripts **now run BOTH `test:integration` and `test:live` by default** as part of the gate (`-SkipIntegration`/`--skip-integration` and `-SkipLive`/`--skip-live` are the explicit escape hatches); running it by hand first is still wise since the scripts also commit/tag/push once it's green.
3. **Repo-hygiene check, then** commit + push to `main` (direct-to-main, no feature branches). Never `git add -A` blind: run `git status --short` AND `git ls-files --others --exclude-standard`, and read the untracked list before staging. Anything machine-specific or agent-local that isn't ignored gets added to `.gitignore` in the same commit rather than committed and cleaned up afterwards — this repo is PUBLIC, so a stray file is published, not just committed. Offenders seen untracked-and-unignored: `.claude/settings.local.json` (machine-specific tool permissions) and ad-hoc `.verification/` output dirs left by an agent. Also confirm nothing under `media/` was hand-edited that a downstream consumer regenerates.
4. **Annotated git tag** `vX.Y.Z` at the release commit → `git tag -a vX.Y.Z -m "Release vX.Y.Z"` → `git push origin vX.Y.Z`.
5. **GitHub Release** for that tag → `gh release create vX.Y.Z --title "Release vX.Y.Z" --notes-file <notes> <vsix>` (notes = the new changelog section(s); include any earlier version that was bumped but never released). **Always attach the `.vsix` that this run of `npm run package` just produced** (`scripts/release.ps1` / `release.sh` do that). Never attach a leftover vsix and never hand-roll `gh release create` around an existing file — `scripts/install.ps1` builds those against staging by design.
   **Desktop installers:** after Open VSX publication, PowerShell runs `gh workflow run desktop-release.yml --ref vX.Y.Z -f release_tag=vX.Y.Z` and checks the release for `.exe`, `.dmg`, and `.AppImage` assets. With Bash, run its printed dispatch command and verify with `gh release view vX.Y.Z --json assets`; the release is not complete until all three artifact types exist.
6. **Store publish — split by store.**
   - **Open VSX: both release scripts run `npm run publish:ovsx`** after creating the GitHub Release, using `OPEN_VSX_API_KEY` from the git-ignored `.env` at the repo root (never print or commit the key). No separate Open VSX publish is needed after the script succeeds.
   - **VS Code Marketplace: manual, Paweł-only.** `npm run publish` (vsce; the `PawelHuryn` publisher is registered + authenticated locally). The agent never runs this — Paweł publishes it himself.
   - **Never announce a store as "live now."** A successful `ovsx publish` is NOT public availability — Open VSX scans new versions before listing them. In issue comments / user-facing messages, say **"~10 minutes"** for BOTH stores (Open VSX and the VS Code Marketplace alike).
   Publishing ≠ tagging either way.

7. **Close the loop on every issue the release fixed — this is part of releasing, not follow-up.** For each one: comment saying what shipped and in which version, apply `done-please-confirm`, and leave it **OPEN** (§ Repo conventions — the reporter decides, and `close-confirmed.yml` closes it after 3 quiet days). Sign the comment per § Repo conventions. Sweep the whole open list, not just the issues named in the changelog: a release sometimes fixes something nobody linked, and a slow-performance report may have a cause that is not ours at all — read the thread before crediting a fix to it.

   **Do NOT label before the fix is installable from the store the reporter actually uses.** The label starts `close-confirmed.yml`'s 3-day clock, so labelling while the VS Code Marketplace still serves the previous version can auto-close an issue the reporter never had a chance to verify — with a message claiming a fix shipped. Step 6 publishes the two stores at different times and by different people, so **the Marketplace publish is the gate**, not the tag and not Open VSX. Commenting earlier is fine (it starts no clock) as long as it says where the build can actually be had.

Don't skip the tag/release (or the vsix asset) on a release push. (A pure mid-dev version bump that isn't a release — e.g. the unreleased v1.3.0 voice iteration — is the only exception.)

## Repo conventions

- **Work on `main`, synced to `origin/main`.** `main` is the only working line — start every task from `main` fast-forwarded to `origin/main`. The `dev` branch is **abandoned** (stale far behind `main`); do **not** develop on it. If the working tree is on `dev`, or `main` is behind `origin/main`, switch to `main` and `git reset --hard origin/main` before doing anything else (the published version lives on `main` — a stale checkout will look many versions behind and misnumber the changelog).
- Direct-to-`main`, no feature branches
- **Never commit or push automatically.** Changes reach `main`/`origin` only on the user's **explicit** request (rare) or as part of a release. Otherwise: build + reinstall locally for testing and leave the working tree uncommitted.
- Commits explain the *why*, not the *what*
- Don't introduce abstractions speculatively
- Don't add comments that explain what well-named code already says
- **Keep `CLAUDE.md` a current-state map** (see the editing-discipline note under § Status): rewrite changed behavior in place, never append changelog narrative or bug post-mortems here — link `research/*.md` / CHANGELOG instead
- 4861 tests is the floor — every PR should keep that green. All tests are grok-free (no binary spawn); grok-dependent probes live in `research/*.cjs` and are run manually, never by `npm test` or CI
- **Rebuilding clears older `.vsix` first** — `npm run package` (and the install/release scripts) delete stale `grok-vscode-phuryn-*.vsix` before building, so only the current version is on disk. `prepackage` then runs `check:relay` (`scripts/check-production-relay.mjs`): `REMOTE_RELAY_URL` must equal `PRODUCTION_RELAY_URL` or the vsix is unbuildable. `install.ps1` is the only path that sets `GROK_ALLOW_STAGING_RELAY_VSIX`; `release.*` unsets it before packaging. After any doc or code change, rebuild + reinstall so the installed extension's bundled docs are current. **Package last:** the vsix bundles `CLAUDE.md`/`README.md`/`docs/` as files, so finish *all* doc + code edits **before** the final `npm run package` + reinstall — otherwise the installed build ships a stale-docs snapshot. If you rebuild mid-task and then touch docs again, rebuild again so the order is always edit-everything → package → reinstall.
- **Version bumps are user-initiated.** Iterate at the current version (rebuild the same vsix and reinstall locally) until the user says to bump and publish. Don't bump `package.json` on your own. When Paweł asks for a release, the default is a **patch** bump (+0.0.1); **any minor or major bump requires his direct, explicit approval** — never infer it from the size of the change.
- **Releasing requires a direct instruction to release — a version number alone is never one.** Only an unambiguous imperative ("release it", "publish 2.0.3", "run the release script") authorizes the § Publishing procedure. Naming a version in any other role does **not**: *"tell them it ships in 2.0.3"*, *"put this under 2.0.3 in the changelog"*, *"this would be a 2.0.3"* are all scope/labelling statements, and treating one as an authorization ships an unrequested tag, GitHub Release, and Open VSX publish — three externally-visible, effectively irreversible actions. The same applies to a release named inside a larger request: the imperative must attach to *releasing*, not to the work. Default to doing the work, leaving the tree uncommitted, and reporting it as ready to release. **In any doubt, ask** — a one-line question costs nothing next to an unrequested publish.

  **An authorization is spent by the release it authorizes.** "Go" ships that version and nothing after it. A bug report about what just shipped is a report, not a renewal — even when the fix is obvious, even when the feature is visibly broken for the person reporting it, even when the version is a patch and needs no version approval. The two are separate questions: **which number** defaults to patch without asking; **whether to ship at all** never does. 3.17.1 was released on that conflation — an owner-reported break in a release minutes old, urgency read as authority. It happened to be a correct fix, which is luck rather than process: a wrong one would have made two bad releases out of one. The shape to recognise is *"they clearly want this, and they said go recently"* — that is precisely the moment to ask, because it is the moment it feels unnecessary.
- **Never close a fixed issue yourself — label it `done-please-confirm` and leave it OPEN.** When a fix ships, reply saying so and apply that label; `.github/workflows/close-confirmed.yml` closes the issue after **3 quiet days**, and any comment from the reporter removes the label so a human takes over. The label is manual-only — the workflow never applies it, and it strips the label from every closed issue so the label list always reads as the live queue. The point is that the reporter, not us, decides whether their bug is actually fixed. Write the reply to match: *"leaving this open for you to confirm"*, never *"closing"*. (Lost during the 2026-08-15 open-sourcing reorganisation and re-learned on #79, where an agent closed a fixed issue outright; the convention had only ever been recorded in a backlog line and in the workflow file itself, so nothing an agent would read before closing.)
- **A contributor stays visible as a contributor.** Any outside contribution reaches `main` with its author's identity intact, so GitHub credits them on the repo's contributor list and the commit shows their name. Merge so their commit survives — never squash someone else's work into a commit authored by us, and never re-implement a PR as our own change. When we adjust a contribution (fixes, review findings, conventions), add commits **on top** of theirs, or if history must be collapsed, carry `Co-authored-by: Name <email>` using the address on their commits. This holds however heavily we rewrite it: the person who found the bug and did the work earns the credit even when little of the original diff survives. Applies to `grok-remote` too — the same rule lives in that repo's `CLAUDE.md`.

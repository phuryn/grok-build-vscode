# CLAUDE.md — grok-build-vscode

VS Code sidebar and desktop client for Grok Build and OpenAI Codex, driven through the [Agent Client Protocol (ACP)](https://agentclientprotocol.com). The host owns presentation and provider metadata; each CLI owns its conversation state, tools, memory, and provider-specific plan enforcement.

The Remote Control server half — the AFK Pilot relay + browser client — is open source at [phuryn/afkpilot](https://github.com/phuryn/afkpilot), which also hosts the system-wide engineering docs (two-repo map, wire contract, auth, test matrix, CI/CD). The wire contract is mirrored: `src/remote-frames.ts` here ↔ `src/frames.ts` there; bump `REMOTE_PROTO_VERSION` in both on any incompatible change, and prefer additive, capability-detected changes. Issues for BOTH repos are tracked here (afkpilot's tracker is deliberately disabled).

## Status

See [CHANGELOG.md](CHANGELOG.md) for the current version and full release history (the Marketplace/GitHub-published build can lag the local working tree). The whole test suite is **binary-free** — CI uses fake Grok and Codex ACP fixtures; binary-dependent probes live separately in `research/*.cjs`. Grok Plan mode is enabled and enforced by the client safety gate (see `research/plan-mode.md` § Resolution); Codex plan review is an ordinary permission whose `allow_once` means implement — write/shell enforcement stays in the adapter/CLI, and Auto accept is suppressed by `effectivePlanActive`. Smoke-tested end-to-end on Linux, Windows-via-WSL, and the **native Windows build** (`irm https://x.ai/cli/install.ps1 | iex`) — `cli-locator` resolves `grok.cmd`/`grok.exe` and `terminal-manager` runs Grok-delegated commands under PowerShell on Windows (`pwsh`→`powershell`, mirroring the standalone CLI; #46), `/bin/sh` elsewhere.

This file is the project map: it describes the **current** architecture, not a per-version log.

**Editing discipline — keep this file lean.** When behavior changes, *rewrite* the affected lines to the new current state; do **not** append a note about what changed or why the old way was wrong. Concretely, none of these belong here:
- version-by-version history or "fixed in 0.2.x / removed in 1.4.x" → [CHANGELOG.md](CHANGELOG.md);
- bug post-mortems / "used to… / this broke because…" narrative → a code comment or `research/*.md`;
- evidence dumps ("one capture: 17.7s", "a real case: 74 messages") → `research/*`.

State the rule, name the function / constant / config-key an agent would grep for, and link the deep-dive — **one fact, one home**. Every feature already has a `research/*.md`; `docs/architecture.md` holds the event-flow detail; [docs/internal/ACP-feedback.md](docs/internal/ACP-feedback.md) is the upstream-facing summary of grok-CLI/ACP friction, agent-family wire differences, and our workarounds (update it when a new workaround lands or an old one becomes obsolete). If a paragraph explains *how we found* a bug rather than *how the code behaves now*, it's in the wrong file.

**Grok CLI compatibility.** `maybeUpdateCliOnUpgrade` runs from session start and updates once after an extension-version change; a fresh install only records `CLI_UPDATE_VERSION_KEY`. Each start then reads `grok --version` via `resolvePlanModeAvailability` (`probeVersionOutput` + `decidePlanModeAvailability`): one short retry on empty/unparseable, then the last verified banner in `grok.cliVersionCache` (`CLI_VERSION_CACHE_KEY`) when the resolved path's mtime/size still match. A successful probe always wins and is what gets cached — the store never overrides a live answer. On Windows, `isStdioBrokenGrokVersion` identifies only the known-broken **0.2.61–0.2.70** startup range and `maybePinBrokenCli` proactively pins it to `GROK_STDIO_DOWNGRADE_TARGET`; `shouldReactivelyDowngrade` → `downgradeBrokenCli` remains the observed-failure backstop above that target. `GROK_REQUIRED_VERSION` and the recovery target share the current supported version (**0.2.117**). A live parseable CLI below the floor latches Plan off for that session (`planModeVersionVerified:true`). An unreadable probe with no matching cache also disables Plan but stays **re-checkable** (`planModeVersionVerified:false`, `planModeAvailability.recheckable`) so picking Plan runs `recheckPlanModeAvailability` without restarting. A cache substitute keeps that availability but is never verified — a stale below-floor banner stays re-checkable (retryable `PLAN_MODE_UNVERIFIED_REASON`, not a permanent version verdict) and a later live probe replaces the stand-in either way. Only a live verified-old answer hard-disables the picker row. Agent/Auto accept still run either way. Agent-initiated/restored Plan raises the client safety gate and returns to Agent. A live untrusted planning turn is cancelled, and the gate drops only after both its `session/prompt` settles and `session/set_mode` confirms Agent; a bounded warning leaves the gate visibly raised if recovery stalls. A stray `exit_plan_mode` receives an error rather than an unsafe native verdict. A later session whose version meets the floor starts with Plan enabled again; existing old processes remain restricted. Exact regression history and probes: `research/stdio-eof-regression.md`; timeline: [CHANGELOG.md](CHANGELOG.md).

## Session pool (Agent Dashboard)

The sidebar runs a **pool of live sessions** (one `grok agent stdio` process each) with one `focused` (the one rendered). Each session's state is a `Session` (`src/session.ts`); the sidebar holds `focused` + a `Set<Session>` `pool`. **Re-focus is lossless**: every session buffers the webview posts that built its chat (`Session.buffer`), so `focusSession` is `clearMessages` + replay of that buffer — no grok reload, no kill, even mid-turn/mid-approval. Clicking a *cold* session (no live process — reaped or pre-window) loads it from disk into a fresh member (`openSession`); a live one re-focuses instantly. Two guards keep it safe: a **per-session `gen`** (bumped only when *that* session's client is torn down, captured by handlers when wired) so a backgrounded session's in-flight events aren't judged stale when focus moves; and **session-scoped `emit(session,…)`** (buffers + forwards only when focused) vs UI-wide `post(…)` (status dots, sessions list). **Status dots.** Every history row shows a dot whose color is a *derived* value (the pure `computeDot` in `src/session-pool.ts`), not the raw `status`: **gray** at rest (idle / read / cold / loaded-from-disk all collapse to one gray — the user never learns warm-vs-cold), **blue** working, **yellow** needs-you, **green** finished-and-unread, **red** errored-and-unread. The green/red is an **unread badge**, not a live state: a turn that ends while the session is *not* focused sets a persisted `unread`/`unreadError` flag in `SessionMetaOverride` (globalState); focusing/opening the session clears it (`markRead`). So the badge **survives reaping AND reload** (it's meta-backed, decoupled from the live process) — that's the payoff: come back and the green dots are exactly the sessions with results you haven't seen. No timer/decay — a never-opened session stays green (it *is* still unread). `computeDot({liveStatus, unread, unreadError})` precedence: working → needs-you → unread(error?) → none. Dots are pushed one-at-a-time via `pushDot`→`sessionDot` (cheap, no disk read) plus a full `dots` map (`dotForId` over disk entries + pool) on each list refresh; palette in CSS — Working=`--vscode-charts-blue`, Needs-you=`--vscode-charts-yellow`, unread=`--vscode-charts-green`, error=`--vscode-errorForeground`, none/default=`--vscode-descriptionForeground`. **Reaping** is the pure `selectReapable` (`src/session-pool.ts`): an **idle TTL** (untouched ≥1h, swept every 5 min) + an **LRU cap** (~8 live; least-recently-used eligible evicted past it), but it **never** reaps the focused or a `working`/`needs-you` session (so the cap can be exceeded when everything spare is busy, by design). Reaping is silent — kill the process, recompute the dot (an unread reaped session **stays green**; a read one goes gray); re-click reloads from disk. Recency (`Session.lastActiveAt`) is stamped on create/focus/made-busy via `touch`. **CLI-update guard:** the explicit *Update Grok Build CLI* action (`updateGrokCliOnDemand`) confirms before tearing the pool down if any session is `working`/`needs-you`; the silent startup auto-update has nothing in flight by construction, so it doesn't ask. Per-workspace scope. The impure `voice-recorder`/`voice-streamer` (ffmpeg spawn + STT fetch/WebSocket) are smoke-tested manually via the `research/voice-*.cjs` probes (`voice-stt-probe`, `voice-e2e-verify`, `voice-stream-probe`, `voice-stream-verify`, `voice-cost-probe`).

**Empty-session cleanup (#24, #97).** Two mechanisms, and the split matters. `parkFocused` / `parkRemoteSession` use `hasHistory === false` to delete an untouched session's on-disk dir the moment the user leaves it, so at most one untitled **New session** exists per view. `sweepEmptySessions` covers what parking cannot reach — a window closed without a prompt, a crashed host, a remote tab that vanished — and runs on activation and after every new/opened session, scoped to that session's repo. It deletes only when `isEmptySession` confirms **zero real user queries** in `chat_history.jsonl`; that content check is authoritative regardless of `num_messages` (an agentic legacy primer turn could balloon past any gate), and `EMPTY_PRIMER_MAX_MESSAGES` now gates only the no-content title fallback. **The predicate used to require our hidden primer, which made it a silent no-op for every session created after v2.2.0 retired it** — that is #97, and the lesson is that a compatibility check keyed on a thing we stopped emitting stops being a check at all. Guards, each load-bearing: live sessions, sessions with a load reservation in flight, renamed, pinned, worktree-bound, `session_kind: "subagent"`, an unreadable (as opposed to absent) history file, and anything newer than `SWEEP_MIN_AGE_MS` (30 min). That last one is sized for the case this process cannot see: **another VS Code window's live sessions are invisible here**, so the delay — plus the fact that only a zero-user-message session is ever swept, and grok re-persists it on its next turn — is what bounds a cross-window delete. It costs nothing, because an orphan is stamped when its window opened and is already old by the next activation. `historyIsIntelligible` is the other interlock and the more important one: "no real user queries" is evidence of emptiness **only if the file could be parsed at all**, because a reader that skips what it doesn't recognize cannot tell "nothing was said" from "grok changed the format" — without it a single CLI schema change turns the sweep into a shredder that finds every session empty. `provenNonEmpty` caches the ids a repo has already cleared so repeat sweeps cost a readdir plus stats, not a re-read of every summary. The newest-`SWEEP_SCAN_LIMIT` slice is joined by every `indexSessions` entry with `hasTranscript === false` (summary-only, no `events.jsonl`) so old probe leftovers cannot hide behind 300 newer conversations. **Verify a predicate change against a real store before shipping it** (`isEmptySession` over `~/.grok`, reporting rather than deleting): the pre-ship dry run covered 1435 sessions and had to show zero candidates carrying a real title or any user query.

**Grok credential probes must not create project history.** `reprobeProviderCredentials` still calls `session/new` (that is the observation), but in a scratch cwd, then `removeSessionFromDisk` after `dispose`. Grok has no ACP `session/delete` (`AcpClient.deleteSession` always throws for that provider); a workspace-cwd probe left a summary-only "Untitled" directory the catalog listed and the CLI could not load. Codex/Claude probes already use scratch + ACP delete. `clearAllSessions` disposes ownerless live pool members in the repo **before** deleting directories (same reason as `deleteSession`) and refreshes the local rail preview.

**History row names (#96).** Precedence is `customName` → grok's own title (`cliSessionTitle`: `session_summary`, else `generated_title`, both rejected when primer-derived) → `autoName` → `Untitled (<date>)`. `maybeGenerateTitle` writes the truncated first user message to **`autoName`, never `customName`** — a name the user typed and a name we guessed are different claims, and writing the guess into the rename field made it permanent, so the CLI's own title for the same session could never surface. Sessions named before this keep what they have: an auto title already sitting in `customName` is indistinguishable from a rename, and guessing wrong there would discard names people typed.

## History pagination

After Grok exhausts, `mergeProviderHistoryPage` continues paging the remaining Codex rows by the requested `limit` and advances the Codex `{updatedAt,id}` high-water cursor; it never emits the whole suffix in one frame.

`buildSessionsList` authorizes the requested cwd before either provider is touched, so a stale or closed remote binding cannot schedule a Codex adapter scan or read/update its cache. The webview auto-requests successive pages while an open list is empty or underfilled, stops at overflow/exhaustion (or a repeated cursor), and keeps an explicit **Load more** button; it never shows `No sessions yet` while `hasMore` is true.

The history popover loads sessions **one page at a time** (`SESSION_PAGE_SIZE = 100`, newest-first) so it stays responsive with thousands of sessions on disk. The cost of the old behavior (read + `JSON.parse` *every* `summary.json` on every open, then render every row) grew linearly and stalled the popover at scale.

**Scope — the selected repo.** `discoverRepos` (`sessions.ts`, pure) enumerates cwd catalogs under `<grokHome>/sessions`, rejecting temp roots and `<grokHome>/worktrees` (a worktree isn't a checkout you choose between). `postSessionsList` indexes the selected repo **plus the worktrees belonging to the same checkout** (`sessionCwdsForRepo` uses the selection's nearest git root when available, otherwise its exact catalog cwd, then `worktreeCwdsForRepo` requires equality with recorded `sourceGitRoot`; `mergeSessionIndexes` combines their catalogs) — this keeps a selected subdirectory and its repository's registered worktrees together without letting an independent nested checkout inherit its parent's sessions. A worktree whose parent identity cannot be established is excluded. `trustedCwds` (the workspace root) bypasses the managed-worktree exclusion so the selection always names a catalog row, or `clearAllSessions`/`selectRepo` would silently no-op. The picker is **remote-only** (`#repo-btn`; in VS Code the window already *is* the repo) and, because the relay serves a client that can outrun the installed extension, the chip appears only once a `repos` frame has arrived — an older host that never sends one shows no chip rather than a dead control. Selection and active conversation are **per browser tab**: `RemoteClientState` maps the current opaque relay client id to its cwd and `Session`; live chat/session UI/voice messages target only that id. `media/chat.js` stores `{repoCwd,id,cwd}` in device-scoped `sessionStorage`, clears it only for an explicit repo/New choice, and posts `selectRepo` + the existing `resumeSession` after each reconnect snapshot. The host attaches that request to an ownerless live pool member (no duplicate process), cold-loads it only when absent, and visibly refuses a missing/deleted session or a session already owned by another tab/VS Code. **Ownership follows the live composer, not focus:** every live session created or adopted by the VS Code dashboard remains locally owned while backgrounded; a departed remote client's member becomes ownerless and reclaimable. Resume transitions serialize by Grok session id; New serializes by client id, while turn/control traffic remains unlocked. The local VS Code webview keeps its independent workspace-root `focused` session. Remote cwd-bearing actions remain gated by `allowRemoteRepoTarget`; roster reconciliation deletes departed client ownership without disposing the pooled session so a new relay id can reclaim it. Pins remain global metadata, while the selected row is per tab.

**Two pure primitives** replace the monolithic full-scan `listSessions` (which is kept only for callers that genuinely need the whole list):

- `indexSessions({fs, grokHome, cwd})` — one `stat` per session dir, **no reads/parses**, returning every id ordered newest-first by transcript (`events.jsonl`) **mtime**, with `summary.json` only as the no-transcript fallback. Opening/restoring may rewrite the summary without conversation activity, so it is not a recency signal. We sort by mtime here *because the id is a UUIDv7 whose timestamp is creation, not last activity* — id-sort would be wrong.
- `readSessionEntries({fs, grokHome, cwd, ids, overrides})` — reads + parses `summary.json` for **exactly the given ids** (the visible page) and applies `customName` overrides. The exact `updated_at` order is re-applied within the loaded page (mtime is only an approximate sort key).

**Host orchestration** (`postSessionsList` in `sidebar.ts`): `indexSessions` orders everything cheaply; a `mtimeById` map drives an **mtime-keyed read cache** (`sessionCache`, `readEntriesCached`) so a re-open / load-more / search reads only entries whose files actually changed — steady-state opens cost ~zero reads. Grok pagination remains the single-provider black box: one consumed-slot page, hidden rows included in `nextOffset`, with exact `updated_at` sorting only inside that mtime-selected page. Codex rows are cheap adapter entries and the per-project cache holds the complete listing. A combined page merges the next Grok page with every Codex row at-or-newer than its oldest visible Grok timestamp; the final Grok page drains the Codex remainder. Its cursor is `{grokOffset,codexHighWater:{updatedAt,id}}`, so no combined code interprets Grok slots or looks ahead. Codex adapter `updatedAt` is stabilized into `SessionMetaOverride.activeAt` on first discovery because `session/load` restamps it; only send advances that host clock optimistically, with turn end reasserting and delayed preview refreshes rechecking the final order. Claude listing time is the SDK's lastModified (`adapterActivityAt`) and is not frozen on first refresh. It posts `{type:"sessions", entries, activeId, dots, offset, total, hasMore, nextOffset, providerCursor, query}`. **Search** is server-side and complete: a non-empty `query` warms the whole Grok catalog once (cache-backed) and filters by display name across both complete provider listings. The cache is invalidated on `rename` (changes displayName without touching mtime), `delete`, and `clearAll`. **Live-session synthesis:** a brand-new session has no provider row yet, so on the **first, unfiltered page** `postSessionsList` injects a synthesized `liveSessionEntry` for any live `pool` member absent from its backing store, carrying its default/remembered provider immediately; the next refresh replaces it once the provider lists it. `hasMore` is computed before injection (load-more pages are store-only), and ids are de-duplicated globally.

**Webview** (`media/chat.js`): `offset === 0` replaces the list, `offset > 0` appends (de-duped by id); a scroll-near-bottom listener requests the next page (`hasMore`/`sessionLoading` guards keep it to one request per boundary); the search box posts a **debounced** (180ms) `listSessions` with the query; a host-driven refresh that arrives unfiltered while a search is active triggers a **sticky-search** re-request so the filtered view isn't clobbered. The "Clear all" footer shows when any non-active session exists (loaded *or* on a later page, via `total`). **Popover positioning:** `positionDropdownPopover` **right-aligns** the popover to the panel edge (`right: 6px`/`left: auto`) and grows it leftward — width-independent, no measurement. It **caps min/max width to the panel** (`min(360|280, parentWidth − 2·EDGE)`, overriding the CSS `min-width: 280px`/`max-width: 360px`) so a long session name **ellipsizes** in a narrow panel instead of overflowing. **Resize/hide:** a `window` `resize` listener re-fits it live while open; a `document` `visibilitychange` listener `closePopovers()` when the view is hidden (a resize while hidden fires no event, so close rather than reappear stale).

**Perf simulation** (`npm run test:perf`, `test/sessions.perf.ts` via `vitest.perf.config.ts`) — opt-in, out of `npm test`/CI. At N=5000 it asserts the op counts: first open drops file reads from **5000 → 100** (~98%), steady-state re-open is **0 reads** (mtime cache), search warms once then **0 reads**, with a modeled-latency projection (~3250ms → ~310ms) and a real in-memory parse-cost wall-clock (~2.7x, disk-latency-free lower bound).

### Test taxonomy — three layers

There are **three** kinds of tests, and it matters which is which:

1. **`npm test` — grok-free unit/DOM/integration suite (3602 tests).** Pure logic, happy-dom tests that drive the real `media/chat.js`, a real-`/bin/sh` TerminalManager smoke, and a fake-CLI ACP integration suite (`test/fixtures/fake-grok-acp.cjs`). **Never spawns the real `grok` binary.** Runs in a few seconds with no network, no login, no subscription. This is the floor — every change keeps it green. (Two separate opt-in suites live outside `npm test`: `npm run test:perf` runs the session-history perf simulation — `test/*.perf.ts` via `vitest.perf.config.ts` — and `npm run test:integration` runs the `@vscode/test-electron` smoke below; both are matched only by their own config so they stay out of `npm test`.)
2. **CI — the *same* suite, plus a REQUIRED Electron smoke.** `.github/workflows/ci.yml`'s `test` job runs `npm ci && npm run compile && npm test && npm run package` on a clean Ubuntu box — **CI's `test` job ≡ layer 1, verbatim** (no `grok` binary, no auth, no subscription, so it *cannot* touch the real CLI — the whole reason layer 1 is grok-free). A second job, `integration`, runs the `@vscode/test-electron` smoke under `xvfb` (`npm run test:integration` — activate the extension, assert commands registered, resolve the webview via the *missing-CLI* onboarding path, then provision `test/fixtures/fake-grok-acp.cjs` through `provisionFakeGrok` so remote resume/`session/load` and matching-sessionId worktree tests run without a real CLI). Test-mode `activate` calls `isolateFromInstalledGrok` before any view can resolve; that latches `testForceMissingGrokCli` so `locateProvider("grok")` will not search config or PATH (an explicit provisioned path still wins). Resume assertions require a distinctive `updates.jsonl` marker to reach the client, `waitForSessionLoad` to settle, and a live ACP session afterward — `initialized` / a reserved session id / replay-before-the-RPC-result are not enough. (`startSession` swallows a failed load and still resolves the reservation.) It's a **required gate** (validated passing against a real VS Code Extension Host before landing; if a Linux/xvfb quirk ever surfaces, fix it rather than demoting the gate). The smoke is still grok-binary-free — it exercises host glue (activation, `getHtml`/CSP, `localResourceRoots`, command registration, hermetic ACP resume) the unit suite structurally can't reach. Compiles in isolation (`integration/tsconfig.json` → `out-integration/`), so it's out of `npm test` and the extension build.
3. **`npm run test:live` — on-demand pre-release suite against REAL grok (`scripts/live-tests.cjs`).** It covers the real handshake, capability drift, prompt/cancel/interject, fork/parallel/restore, plan enforcement, rewind, usage, and generative surfaces. The plan lane now uses native verdicts: its first same-turn `exit_plan_mode` response is `cancelled`, the second is `approved`, and the gate is lowered inside that response callback before implementation continues; `plan-cancel-rewind` uses native `abandoned` with no primer or marker turns. It reuses the compiled dispatch/gate/rewind modules and shipped webview helpers. The release scripts run it by default, but it needs a logged-in grok, burns credits, and never belongs in `npm test` or CI. A SKIP does not fail the gate; research probes remain manual one-offs.

**So:** local `npm test` == CI's `test` job (both grok-free) — but that is NOT all of CI: a second required job runs the grok-free Electron smoke, so `npm test` alone is a subset of what must pass. Mirror it with `npm run test:integration`, which `release.*` now gates on too. The real-grok tests are a separate, mandatory pre-release gate — always run before a tag/release (no need to ask), never on every commit.

**Standing test discipline.** Every `session.provider === …` branch has both-provider coverage. A wrapper that assumes a function's documented invariants carries that function's contract tests, including consumed-slot pagination. External-artifact fixtures mirror the real listing and layout, including multi-platform bundles and the Codex package structure. Every new filesystem or network stream has fault-injection coverage for asynchronous error paths.

### grok CLI version + updating

The native-Windows build (`irm https://x.ai/cli/install.ps1 | iex`) installs from the **stable** channel. The extension pins Windows to the supported build (`GROK_STDIO_DOWNGRADE_TARGET` in [src/cli-locator.ts](src/cli-locator.ts); see § Status → Grok CLI compatibility). **grok does not auto-update.** Updating is the explicit `grok update` command: `--check [--json]` checks without installing, bare `grok update` installs the latest on the current channel, `--stable` (default, weekly) / `--alpha` switch channels, `--version <X.Y.Z>` pins a build. `grok update` can only rename the binary when no grok process holds it open (else *"cannot rename locked executable"*), so the extension's update path tears the whole pool down and **awaits each process's actual exit** before updating; on Windows it `taskkill /T /F`-kills the process **tree** (grok backgrounds children that keep the binary locked) and retries once on a lingering lock (`isLockedBinaryError`). Re-run `npm run test:live` after any CLI update — the wire format is the thing that drifts.

The gutter track sizes per region to the widest number rendered (`--tdl-num-w` = `max(4ch, digits+1)`) — 4ch through 999, wider only for a 1000+ line file. The `+/−` glyph is a color-blind affordance beside the border. Colors are **Codex's exact palette** (`--tdiff-*` CSS vars, dark default + `body.vscode-light` override): add `#40c977`/`#00a240`, del `#fa423e`/`#ba2623`, backgrounds the same at 23%/15% alpha — reused for the `+N −M` stat too. `applyToolDiffs`/`attachDiffPreviewToToolItem` handle BOTH the live `tool_call_update` and the session-load completed `tool_call` replay shapes (#30); a single call can carry multiple `diff` blocks (rendered as an array), each getting exactly **one** `open diff →` (per-site would emit 148 buttons; its payload stays the block's own `oldText`/`newText`). **grok reports each edit's diff twice** — an optimistic pre-write echo, then the authoritative completed update — and for a whole-file Write that OVERWRITES a file the echo carries `oldText:""` while the completed one carries the real prior content, so the echo must not win: idempotency is keyed on `item._diffSig` (the serialized diffs, **sites included**, so the `details[]`-seeded render outranks the echo's approximate one), making an identical replay a no-op while a *different* later diff repaints the row (reusing the detail node, or `wireCommandToggle`'s listener would strand + double-bind). **Totals paint as each edit lands**, not at batch close — the data is on the wire ~2.2–3.3s before the turn ends (`research/edit-diff-timing-probe.cjs`). `recomputeGroupDiffTotals` *recomputes* from the rows' `_diffStat` (so a corrected row replaces rather than double-counts) and `paintGroupDiffTotals` owns a `.tool-group-diff-totals` span, re-painted after each of the two things that wipe the header: `addToToolGroup`'s per-call `hdr.innerHTML` rebuild and `closeToolGroup`'s label reset. Painting earlier still, from the initial `tool_call`'s `rawInput`, is deliberately NOT done: it buys ~30ms and reconstructs the same wrong `oldText:""` for a Write. None of this expands anything — totals ride the *collapsed* header; only `grok.expandCommandOutputs` / the latch open rows. The native `open diff →` link (→ `sidebar.ts` diff editor) stays on VS Code and older hosts; desktop `previewInApp` routes it into the same overlay at full size (`requestDiffPreview`) instead of a bare window. `summarizeTools` counts edits by unique `toolFilePath` so "Edited N files" matches the deduped header totals.
- **Generated media (v1.4.x).** `/imagine` and `/imagine-video` report generated paths in completed tool results. `isMediaGenToolCall` / `extractGeneratedMediaPaths` detect them; `postGeneratedMedia` forwards only paths whose canonical targets remain in the provider's generated-media root. `asWebviewUri` streams trusted files; a size-capped `data:` fallback is allowed only after that trust check when the surface has no served root. Codex inference additionally requires UUID / `exec-UUID` adapter ids and resolved containment under `generated_images`. Wire format + probes: `research/image-generation.md`.
- **Subagent rows.** A delegation is a tool call whose `_meta["x.ai/tool"].name` is `spawn_subagent` (grok-build) or `Task` (the Composer agent) — that marker is **authoritative both ways** for the pure classifier (`isSubagentToolCall`, `webview-helpers.js`): grok titles Grep/Read calls with their query/filename, so a grep FOR "spawn_subagent" is titled exactly that and title matching false-cards; without `_meta`, exact tool names + `rawInput.subagent_type` + the legacy background heuristics apply (the `get_command_or_subagent_output` poller stays excluded). The row renders *Subagent · \<description\>* (never downgraded by Composer's untitled completion update — `setSubagentTitle`) with blink-dots, then a duration stamp and a click-to-expand result under an "Output of the subagent:" label; `cleanSubagentOutput` strips the CLI envelope (plumbing tags, lead-ins, one wrapping `<response>` pair, the Agent ID hint) — every pattern optional and never throwing. Completion shapes differ: grok-build's foreground `tool_call_update` carries `rawOutput.SubagentCompleted` (output + duration_ms); Composer's carries only untitled text (`rawOutput {type:"Text"}`, no duration); a **background** spawn "completes" instantly with a started-ack (skipped — not the result) and its real output arrives on the `get_command_or_subagent_output` poller's `TaskOutput`, matched back to the card by task id (`maybeFinishSubagentFromTaskOutput`). **On cold `session/load` that poller output is FLATTENED to a text blob** (`=== Task … === / Command: [subagent:…] / … / === Output ===`, not the live structured shape), so the restore path parses it back with the pure `parseSubagentTaskResult` (`webview-helpers.js`, subagent-only — a backgrounded shell command polls the same tool and is left as a normal row) and `maybeFinishSubagentFromTaskText` folds it into the card + drops the redundant poller row (else a restored background delegation showed a stuck card + a raw `[subagent:…]` row). **Failure/cancel are threaded through BOTH the tool-channel completion AND the lifecycle rail** (a completion routinely races ahead of the lifecycle, so the marker can't live only on one) — a failed card reads red (`.subagent-failed`), a cancelled one muted (`.subagent-cancelled`); `finishSubagentCard`'s already-done early-return upgrades a late status marker, not just a late duration. The restore-created card is marked `subagentReplayed` and excluded from **live** lifecycle matching (mis-attribution guard) but NOT during replay (`state.replaying || !replayed`), so it still consumes its own re-forwarded lifecycle. The `subagent_spawned`/`subagent_finished` lifecycle stream is delivered **two ways**: on the LIVE `_x.ai/session_notification` rail (→ `xaiNotification`; the pure `isSubagentLifecycleUpdate` in `acp-dispatch.ts` re-routes it to the same `subagentUpdate` channel the webview consumes) and on the persist/replay `_x.ai/session/update` rail (→ `subagentLifecycle` → `subagentUpdate`, for `session/load`). `subagent_finished` fills `duration_ms` + the child's output — the duration Composer's tool-channel completion lacks (probe-confirmed on 0.2.101; earlier 0.2.93 measurements watched only the persist rail, which never fires live, hence the old "the CLI only logs these" note). Lifecycle tagging prefers an exact `subagent_id` match and only then the first untagged FIFO card (`tagSubagentChildSession`) — a started-ack can tag card A before `subagent_spawned`, so FIFO-first would steal B. A history replay settles never-completed rows at replay end. On grok **1.0.3+** the CLI multiplexes every session onto one stdout (`params.sessionId` is the demux key; captured 2026-08-14): child prose, thoughts, and tool calls arrive live on the child's sessionId after `subagent_spawned` (`child_session_id`). `parseAcpLine` keeps that id; `isForeignSessionUpdate` / `handleSessionUpdate` emit them as additive `childStream` host messages into the matching card (never the parent transcript). A child tool row closes the open prose segment (`closeChildProseSegment`) so the next chunk opens a new `.subagent-prose` below it — the same close-on-tool interleave as the parent transcript. Word-level child chunks batch through `requestAnimationFrame` per card (`scheduleChildStreamFlush` / `flushChildStream`), matching `appendAgent`/`flushAgent`. A child chunk whose session matches no card is dropped. Composer-era CLIs never send child streams — `test/fixtures/composer-subagent-session.jsonl` still pins that shape. grok persists each child as a **top-level sibling session** with `session_kind: "subagent"` — the history list hides those (`SessionListEntry.kind` from `buildEntry`, filtered in `postSessionsList`, which pages by index slots consumed — the `nextOffset` field on the `sessions` message — so hidden rows can't stall or duplicate load-more). Cold `session/load` still does not replay child transcripts into the parent; cards rebuild from the lifecycle rail. Real wire captures: `test/fixtures/composer-subagent-session.jsonl` (replayed by `test/subagent-replay.dom.test.ts`) and `test/fixtures/grok-subagent-mux.jsonl` (replayed by `test/subagent-mux.dom.test.ts`); deep-dive: `research/subagents.md`.
- **Logout (#13).** `grok.logout` command + gear-menu *Sign out* → `sidebar.logout()`. Codex observes `codex logout` success before reset; Grok retains its terminal flow. `resetProviderSessionsAfterLogout` synchronously detaches focused, background, active-remote, and detached-tab sessions before persisted connection-state writes or replacement starts can stall. Drafts with conversation ids enter META before disposal and leave it only after startup succeeds **and a focused/attached composer exists**; detached tabs retain META through desk-first sign-in and restore on their own same-provider, other-provider, or needs-provider reattachment. ## Cross-platform notes

- `terminal-manager.ts` selects the shell via `resolveTerminalShell(platform, resolve, pref)`: Windows runs the agent's commands under PowerShell (`pwsh.exe`→`powershell.exe`, else cmd.exe via `shell:true`) to mirror the standalone CLI (#46); everywhere else `shell:true` → `/bin/sh`. Node runs a string shell as `<shell> -c "<command>"` (pwsh + Windows PowerShell both accept `-c`, and Node passes the command string through faithfully — embedded double quotes / JSON / paths-with-spaces survive; only cmd/bash-style `\"` escaping doesn't, which grok won't emit for a PowerShell target). `whichOnPath` skips the `\WindowsApps\` Store-alias stub. `grok.terminalShell` (`"auto"`|`"cmd"`, host-read → `setTerminalShellPreference`, cache-clearing) is the escape hatch back to cmd. Don't hardcode shell paths. **The agent is told which dialect to WRITE for** via `GROK_SHELL` in its spawn env (`buildEnv` in `sidebar.ts` sets it from the pure `grokShellEnvValue(resolvedTerminalShell(), platform)` — `pwsh`/`powershell`/`cmd` on Windows, unset on POSIX, and never overriding a user-set value): grok's ACP mode otherwise describes the shell from its own host detection and can emit POSIX idioms for a PowerShell host (§2.9; the `Shell:` line in the model's first message tracks `GROK_SHELL`, `research/oss-surfaces-probe.cjs`). **The `pwsh`-vs-`powershell.exe`-fallback gap is real: Windows PowerShell 5.1 collapses any non-zero native exit to 1 (pwsh 7 preserves it) and rejects `&&`/`||` chains (pwsh 7 accepts them) — install pwsh 7 for full parity.** A fresh shell spawns per command, so the profile re-runs each time (matches standalone's reachable functions, but adds latency and any profile stdout can prepend to captured output; on a `Restricted` execution policy 5.1 skips the profile + warns). The agent only acts on zero-vs-non-zero, which is preserved. Root cause + probe evidence: `research/powershell-terminal.md`.
- `cli-locator.ts` reads `HOME` / `USERPROFILE` env vars first (testability), falls back to `os.homedir()`. Uses `where` on Windows, `command -v` elsewhere. Checks `.cmd`/`.exe`/`.bat` extensions on Windows.
- Tests use `node -e "..."` everywhere, so commands are deterministic across platforms — don't add `pwd`, `awk`, `sleep`, `true`, etc.

## Publishing

**Release procedure — ALWAYS tag + create a GitHub Release (with the `.vsix` attached) on a release push to `main`** (standing convention; mirrors the `v1.0.0…` tag history + GitHub Releases):

**The whole procedure below (steps 2–5) is scripted** — after bumping the version + writing the changelog section (step 1, user-initiated), just run:

```bash
pwsh scripts\release.ps1        # Windows (native) — what we use here
./scripts/release.sh            # macOS / Linux / WSL
```

It reads the version from `package.json`, runs the gate, builds the vsix, commits the working tree (`-MessageFile`/`-Message` override the default `Release vX.Y.Z`), pushes `main`, creates the annotated tag, and runs `gh release create` **with the vsix attached** — extracting the matching `## X.Y.Z` changelog section as the release notes. `-DryRun`/`--dry-run` previews; `-NoTest`/`--no-test` skips the gate. It refuses to run off `main` or when the tag already exists (i.e. the version wasn't bumped). The script does **not** call `vsce`/`ovsx`, and there is **no publish workflow** (`.github/workflows/` is just `ci.yml`) — so the GitHub Release does **not** auto-publish to any store. Store publishing is split by who runs it (step 6): the agent **always publishes Open VSX right after the script succeeds** (part of every release, no separate ask); the **VS Code Marketplace** is manual and Paweł-only.

What the script encodes, step by step:

1. Bump `version` in `package.json` (user-initiated) and add the dated section to `CHANGELOG.md`. As part of this pass, **review the release-facing docs for staleness against what actually ships** — this review is a required step, not optional:
   - `README.md` — features / screenshots / install matrix.
   - **`README.marketplace.md` — the STORE listing, and a separate file.** `npm run package` ships it via `vsce package --readme-path`, so this is what the VS Code Marketplace and Open VSX render; `README.md` is only the GitHub page. Every edit to one is a decision about the other: the two carry the same feature list (keep the ordering in step), but deliberately different heroes — the listing sells the **extension**, so a desktop-app screenshot is off-message there. Its images are absolute `raw.githubusercontent.com/…/main/…` URLs, so **deleting or renaming anything under `docs/screenshots/` breaks the published store page** — remotely, after the release, with nothing local to notice. 3.2.1 shipped exactly that (alt text and a broken-image icon on Open VSX) because only `README.md` was updated. `test/readme-images.test.ts` now fails on a dangling reference in either file; it does not check that the two agree on content, which stays a judgement call.
   - `TESTS.md` — test plan vs. what actually ships.
   - `CLAUDE.md` — the project map (§ Module map, § ACP surfaces, § Known limits, the test-count floor): does it still describe the current architecture? It deliberately **doesn't** hardcode the version (it points to the changelog), so it needs no version edit — but its prose can go stale as behavior changes.
   - `docs/architecture.md` — the architecture doc: keep it in sync with new modules / event flows / surfaces.
   - `package.json` itself — description, `engines`, `categories`, `contributes`.

   Keep `CHANGELOG.md` entries **terse** (1–3 bullets per release under Added/Changed/Fixed; deep detail belongs in commits / `research/`, not the changelog); releases before the current minor live in `docs/CHANGELOG-ARCHIVE.md` (linked from the foot of `CHANGELOG.md`).
2. `npm test` (3602-test floor, all green) + `tsc -p . --noEmit` clean + **`npm run test:integration`** (the real Extension Host — `npm test` is only CI's `test` job, and CI runs this as a SECOND required job; without it a release can be tagged and published before CI goes red), **and `npm run test:live` against real grok — mandatory, run without asking**. The `release.*` scripts **now run BOTH `test:integration` and `test:live` by default** as part of the gate (`-SkipIntegration`/`--skip-integration` and `-SkipLive`/`--skip-live` are the explicit escape hatches); running it by hand first is still wise since the scripts also commit/tag/push once it's green.
3. **Repo-hygiene check, then** commit + push to `main` (direct-to-main, no feature branches). Never `git add -A` blind: run `git status --short` AND `git ls-files --others --exclude-standard`, and read the untracked list before staging. Anything machine-specific or agent-local that isn't ignored gets added to `.gitignore` in the same commit rather than committed and cleaned up afterwards — this repo is PUBLIC, so a stray file is published, not just committed. Offenders seen untracked-and-unignored: `.claude/settings.local.json` (machine-specific tool permissions) and ad-hoc `.verification/` output dirs left by an agent. Also confirm nothing under `media/` was hand-edited that a downstream consumer regenerates.
4. **Annotated git tag** `vX.Y.Z` at the release commit → `git tag -a vX.Y.Z -m "Release vX.Y.Z"` → `git push origin vX.Y.Z`.
5. **GitHub Release** for that tag → `gh release create vX.Y.Z --title "Release vX.Y.Z" --notes-file <notes> <vsix>` (notes = the new changelog section(s); include any earlier version that was bumped but never released). **Always attach the `.vsix` that this run of `npm run package` just produced** (`scripts/release.ps1` / `release.sh` do that). Never attach a leftover vsix and never hand-roll `gh release create` around an existing file — `scripts/install.ps1` builds those against staging by design.
6. **Store publish — split by store.**
   - **Open VSX: ALWAYS published by the agent as part of every release** (immediately after step 5, no separate ask) — `npx ovsx publish grok-vscode-phuryn-<version>.vsix -p <key>` with the key read from `OPEN_VSX_API_KEY` in the git-ignored `.env` at the repo root (never print or commit the key).
   - **VS Code Marketplace: manual, Paweł-only.** `npm run publish` (vsce; the `PawelHuryn` publisher is registered + authenticated locally). The agent never runs this — Paweł publishes it himself.
   - **Never announce a store as "live now."** A successful `ovsx publish` is NOT public availability — Open VSX scans new versions before listing them. In issue comments / user-facing messages, say **"~10 minutes"** for BOTH stores (Open VSX and the VS Code Marketplace alike).
   Publishing ≠ tagging either way.

Don't skip the tag/release (or the vsix asset) on a release push. (A pure mid-dev version bump that isn't a release — e.g. the unreleased v1.3.0 voice iteration — is the only exception.)

## Repo conventions

- **Work on `main`, synced to `origin/main`.** `main` is the only working line — start every task from `main` fast-forwarded to `origin/main`. The `dev` branch is **abandoned** (stale far behind `main`); do **not** develop on it. If the working tree is on `dev`, or `main` is behind `origin/main`, switch to `main` and `git reset --hard origin/main` before doing anything else (the published version lives on `main` — a stale checkout will look many versions behind and misnumber the changelog).
- Direct-to-`main`, no feature branches
- **Never commit or push automatically.** Changes reach `main`/`origin` only on the user's **explicit** request (rare) or as part of a release. Otherwise: build + reinstall locally for testing and leave the working tree uncommitted.
- Commits explain the *why*, not the *what*
- Don't introduce abstractions speculatively
- Don't add comments that explain what well-named code already says
- **Keep `CLAUDE.md` a current-state map** (see the editing-discipline note under § Status): rewrite changed behavior in place, never append changelog narrative or bug post-mortems here — link `research/*.md` / CHANGELOG instead
- 3602 tests is the floor — every PR should keep that green. All tests are grok-free (no binary spawn); grok-dependent probes live in `research/*.cjs` and are run manually, never by `npm test` or CI
- **Rebuilding clears older `.vsix` first** — `npm run package` (and the install/release scripts) delete stale `grok-vscode-phuryn-*.vsix` before building, so only the current version is on disk. `prepackage` then runs `check:relay` (`scripts/check-production-relay.mjs`): `REMOTE_RELAY_URL` must equal `PRODUCTION_RELAY_URL` or the vsix is unbuildable. `install.ps1` is the only path that sets `GROK_ALLOW_STAGING_RELAY_VSIX`; `release.*` unsets it before packaging. After any doc or code change, rebuild + reinstall so the installed extension's bundled docs are current. **Package last:** the vsix bundles `CLAUDE.md`/`README.md`/`docs/` as files, so finish *all* doc + code edits **before** the final `npm run package` + reinstall — otherwise the installed build ships a stale-docs snapshot. If you rebuild mid-task and then touch docs again, rebuild again so the order is always edit-everything → package → reinstall.
- **Version bumps are user-initiated.** Iterate at the current version (rebuild the same vsix and reinstall locally) until the user says to bump and publish. Don't bump `package.json` on your own. When Paweł asks for a release, the default is a **patch** bump (+0.0.1); **any minor or major bump requires his direct, explicit approval** — never infer it from the size of the change.
- **Releasing requires a direct instruction to release — a version number alone is never one.** Only an unambiguous imperative ("release it", "publish 2.0.3", "run the release script") authorizes the § Publishing procedure. Naming a version in any other role does **not**: *"tell them it ships in 2.0.3"*, *"put this under 2.0.3 in the changelog"*, *"this would be a 2.0.3"* are all scope/labelling statements, and treating one as an authorization ships an unrequested tag, GitHub Release, and Open VSX publish — three externally-visible, effectively irreversible actions. The same applies to a release named inside a larger request: the imperative must attach to *releasing*, not to the work. Default to doing the work, leaving the tree uncommitted, and reporting it as ready to release. **In any doubt, ask** — a one-line question costs nothing next to an unrequested publish.
- **Never close a fixed issue yourself — label it `done-please-confirm` and leave it OPEN.** When a fix ships, reply saying so and apply that label; `.github/workflows/close-confirmed.yml` closes the issue after **3 quiet days**, and any comment from the reporter removes the label so a human takes over. The label is manual-only — the workflow never applies it, and it strips the label from every closed issue so the label list always reads as the live queue. The point is that the reporter, not us, decides whether their bug is actually fixed. Write the reply to match: *"leaving this open for you to confirm"*, never *"closing"*. (Lost during the 2026-08-15 open-sourcing reorganisation and re-learned on #79, where an agent closed a fixed issue outright; the convention had only ever been recorded in a backlog line and in the workflow file itself, so nothing an agent would read before closing.)

Pick by whether Paweł actually reviewed the text before it was posted: if he reviewed it, use `_Written with an agent, reviewed by Paweł_`; if the agent posted it without his review, use `_Written by Pawel's agent_`. Only claim review when it actually happened.
- **The `phuryn` GitHub account is Paweł** — the user you are working with and the repo owner. Unsigned comments from `phuryn` are his own words (don't read them as a third party's); agent-posted comments carry the signatures above.
